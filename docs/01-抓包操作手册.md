# 抓包操作手册（阶段 A）

> 目标：拿到官方蓝牙钥匙的**空口原始数据**，回答"协议能不能被重实现"这个问题。
> 全程 **不需要 root、不需要硬件嗅探器、不需要改动官方 APP**。
> 耗时约 30 分钟。

---

## 0. 原理说明（为什么这不算"调试官方 APP"）

Android 系统蓝牙栈自带一个 HCI 日志开关，它记录的是**手机蓝牙芯片与系统之间的原始数据流**——
也就是空口上真正发出去和收到的东西。这属于**系统层抓包**，跟官方 APP 的进程、代码、内存
完全无关，APP 既感知不到，也没有任何东西被注入。

拿到这份日志，就等价于把一个蓝牙嗅探器放在了手机和车之间。区别只是我们不需要买硬件。

---

## 1. 准备工作

| 项目 | 要求 |
|---|---|
| 手机 | Android 8.0 以上，**不需要 root**。建议用备用机 |
| 车辆 | 领克 08，电量充足（低压电池别亏电） |
| 领克 APP | 已登录、蓝牙钥匙已激活、能正常手动解锁 |
| 环境 | 地面空旷处，周围少 Wi-Fi/蓝牙干扰源 |
| 时间 | 约 30 分钟，需要你在车旁来回走动 |

> ⚠️ **抓包期间不要同时做别的事**（开后备箱、调空调、连 CarPlay）。
> 每多一个动作，时间轴就多一段噪声，后面解读更费劲。

---

## 2. 打开 HCI 日志开关

```
设置 → 关于手机 → 连续点击「版本号」7 次 → 进入开发者模式
设置 → 系统 → 开发者选项 → 找到「启用蓝牙 HCI 信息收集日志」→ 打开
```

**关键一步：关闭蓝牙，再重新打开。** 不重启蓝牙，开关不会生效。

### 国产 ROM 差异

| ROM | 情况 |
|---|---|
| MIUI / HyperOS | 选项名「开启蓝牙 HCI 信息收集日志」，在开发者选项靠下位置 |
| ColorOS / OriginOS | 可能在「开发者选项 → 蓝牙」分组内，或在搜索框搜「蓝牙」 |
| HarmonyOS | 部分版本隐藏该项，需在开发者选项搜索「HCI」 |
| 原生 Android | 一定有，Developer options → Enable Bluetooth HCI snoop log |

找不到时的兜底：部分机型可通过 `adb shell settings put global bluetooth_hci_log 1` 打开
（需 USB 调试），然后重启蓝牙。

---

## 3. 清掉旧日志

先确认旧日志是否存在，避免新旧数据混在一起导致时间轴错乱：

- 文件管理器进「内部存储」根目录，看有没有 `btsnoop_hci.log`
- 有的话改名为 `btsnoop_hci.old.log` 备份

---

## 4. 标准采集动作序列 ⭐ 最重要

**核心纪律：每个动作之间停 3 秒，心里默数。** 后面要靠时间间隔来切分操作。

| # | 动作 | 停顿 |
|---|---|---|
| 0 | 站在车 **5 米外**，确认 APP 已登录、蓝牙开 | — |
| 1 | 走到车旁 1 米，打开 APP，等它显示「已连接」 | 3s |
| 2 | 点「**解锁**」 | 3s |
| 3 | 点「**上锁**」 | 3s |
| 4 | 点「**解锁**」 | 3s |
| 5 | 点「**上锁**」 | 5s |
| 6 | 走到 **20 米外**，站住不动 | 10s |
| 7 | 走回车旁，等 APP 重新连上 | 3s |
| 8 | 点「**解锁**」 | 3s |
| 9 | 点「**上锁**」 | 3s |
| 10 | 关闭日志开关（或直接拔线） | — |

### 为什么必须做满 3 轮解锁

比对三轮的载荷才能判断有没有**防重放机制**（闸门 G3）：

- 三轮载荷**完全相同** → 大概率可重放，项目可行性大幅提高
- 三轮载荷**有字节在变** → 存在计数器/nonce，必须真正实现算法（工作量大但仍可能可行）
- 长度都不一样 → 变长编码，通常含计数器

只抓一轮的话，这一步没法判断。

### 第 6 步为什么重要

走到 20 米外是为了让车机**断开并进入休眠**。很多数字钥匙在休眠态和唤醒态的握手流程不一样，
这一步能抓出"冷启动握手"，而冷启动恰恰是无感解锁最常踩坑的地方。

## 5. 导出日志

### 方式一：adb（推荐，最省事）

```bash
adb pull /sdcard/btsnoop_hci.log captures/btsnoop_hci.log
```

### 方式二：不用 adb

1. 文件管理器 → 内部存储根目录 → 找到 `btsnoop_hci.log`
2. 重命名成 `btsnoop_lyk08_20261110.log`（带上日期）
3. 通过微信文件传输助手 / 数据线拷到电脑
4. 放进项目的 `captures/` 目录

### 方式三：部分机型的其他路径

| 路径 | 说明 |
|---|---|
| `/sdcard/btsnoop_hci.log` | 最常见 |
| `/data/misc/bluetooth/logs/btsnoop_hci.log` | 需要 root |
| `/sdcard/Android/data/.../files/` | 极少数 ROM |

## 6. 跑分析

```bash
cd lynkco-passive-key
python tools/btsnoop_analyze.py captures/btsnoop_hci.log -o captures/report.md --json captures/report.json
```

会输出一份 Markdown 报告，含：

1. **GATT 服务与特征 UUID 完整清单** ← 自研 APP 要连的服务表
2. **写帧清单**（手机→车机的每一条命令，十六进制）
3. **通知帧清单**（车机→手机）
4. **写帧差异分析** ← 判定 G3 防重放
5. **SMP 配对流程** ← 判定 G1
6. **闸门速览**

## 7. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 文件不存在 / 0 字节 | HCI 开关没生效 | 关蓝牙→开蓝牙；或重启手机后再试 |
| 有 ATT 事件但没有写帧 | APP 没真正下发命令，或只连了没操作 | 确认点了解锁按钮；重抓 |
| 没有服务发现流程（0x10/0x11） | APP 用了缓存的服务表（之前配对过） | 在系统蓝牙设置里「忘记此设备」，重抓一次 |
| 抓包时长很短 | 日志在操作前被截断 | 先清日志，再开始操作 |
| 时间戳看着不对 | 部分机型 btsnoop 时间戳精度不同 | 不影响相对顺序，忽略绝对值 |
| 报「不是 btsnoop 文件」 | 抓到的是其他格式（.cfa/.pcap） | 确认文件名是 `btsnoop_hci.log` |

---

## 8. 隐私提醒

这份日志里会包含：

- 手机与车机的**蓝牙 MAC 地址**
- 车机广播的**厂商数据**
- 也可能出现与车辆身份相关的标识

自己分析没问题。**如果要发给别人看，先把 MAC 和厂商数据段打码。**

---

## 9. 抓完之后

把 `captures/report.md` 发我。我会据此判断：

- **G1 是否命中**（有没有 BLE 配对绑定）—— 命中就可以提前收工
- **G3 的形态**（静态帧 / 计数器 / 变长）—— 决定后续实现难度
- **GATT 拓扑**（服务与特征结构）—— 直接作为自研 APP 的连接依据

然后才决定要不要进阶段 B（APK 静态逆向）。
