# 架构与工作原理

## 一句话

**不搬钥匙，只在官方 APP 自己的进程里"代按按钮"。**

凭证（白盒 SM4 密钥、Keystore 条目、车厂 CA 证书）全部留在官方 APP 里不动。
我们的模块被 LSPosed 注入官方 APP 进程，用反射直接调用它内部的
`NearbyControlSend.sendControlCmd(...)`，车端看到的始终是官方 APP 本人。

这就绕开了此前判定为"物理不可行"的两道锁：

| 原死锁 | 为什么现在不是问题 |
|---|---|
| G2 密钥在 TEE / 白盒绑签名 | 不导出密钥，调用的就是原本的进程与身份 |
| G4 车端只信车厂 CA 证书 | 认证仍由官方 APP 用自己的 signCert 完成 |

## 为什么感知层放在官方 APP 进程里

这不是设计偏好，是被系统逼出来的。三个实测结论：

1. **抽象 LocalSocket 跨 UID 被 SELinux 拒绝**
   `IOException: Permission denied`。Android 12+ 收紧了 `unix_stream_socket connectto`。

2. **显式广播可以，但回执会被冻结器拦截**
   `Greezer Denial: ... due to receiver ... need cached broadcast`
   HyperOS 的 Greezer 把我们的进程判为 cached，回执送不回来。

3. **我们的进程在后台直接被冻**
   `ps` 显示状态为 `do_freezer_trap`，线程拿不到 CPU，持续扫描必然停摆。

而 `com.lynkco.customer:dkservice` 常驻、持有 `BLUETOOTH_SCAN` /
`BLUETOOTH_PRIVILEGED` / `ACCESS_BACKGROUND_LOCATION`，且官方 APP 本身就为
蓝牙钥匙做了保活（`ThirdAdapterAliveStrategy`、`libhigh_available_android.so`）。

所以：**感知层搬进官方 APP 进程，搭它的保活便车**，顺带把跨进程延迟降到零。
自研 APP 退化为配置端，被冻结也不影响功能。

## 距离判定：滞回 + 真实时间驻留

参数出厂值：**解锁 -75 dBm / 上锁 -82 dBm / 驻留 4.5 s**。

RSSI 取 8 点滑动窗口中位数，抑制单包抖动。判定带滞回：
解锁看 `≥ -75`，上锁看 `≤ -82`，中间 7 dB 是死区，防止在边界反复触发。

关键一点：**驻留按时间算，不按采样次数算**。早期实现用"连续 N 次采样"计数，
但扫描回调频率随广播间隔、系统调度变化（约 0.3~1 s 一次），
同样的 N 在不同时刻代表不同时长，4.5 s 这种精确值无法表达。
现在改为记录"连续满足条件的起始时刻"，`now - sinceAt >= dwellMs` 才动作，
得到的是真实时间，手感稳定。

## 扫描为什么必须带 ScanFilter

Android 对**无过滤**的后台扫描有严格限流（息屏后大约每 30 分钟只给几秒窗口）。
带 `ScanFilter(deviceAddress)` 的扫描不受该限制 —— 这是能长期后台工作的前提。

因此 `ModuleWatcher` 一律使用 MAC 过滤，MAC 来自官方 APP 自己的 MMKV
（`files/mmkv/ble_sdk` 的 `dk_connected_mac`，明文可读）。

## 命令协议（广播）

请求 `com.pkauto.passivekey.CMD`，回执 `com.pkauto.passivekey.RESP`。
强制 `setPackage` 定向；带共享 token；API 34+ 还校验发送方 UID 必须是控制端。

| 命令 | 作用 |
|---|---|
| `PING` | 探活，返回 MAC 与 dkId 摘要 |
| `STATUS` | 桥接状态 + BLE 连接状态 |
| `ENUMS` | 列出可用的 BleControlType / CmdChannel |
| `CONFIG near,far,nearDwellMs,farDwellMs` | 下发感知参数（驻留单位毫秒，例 `CONFIG -75,-82,4500,4500`） |
| `START` / `STOP` | 启停模块内感知 |
| `WSTATE` | 查询感知运行状态与命中次数 |
| `UNLOCK` / `LOCK` | 直接下发解锁/上锁 |
| `APPROACH_ON/OFF`、`WALKWAY_ON/OFF` | 开关车端的靠近解锁/远离锁车功能位 |
| `DOOR` | 走高层 `NearbyControlImpl.controlDoor` 降级路径 |
| `SCANALL` / `SCANRESULT` | 10 秒无过滤诊断扫描 / 读取附近设备列表 |

## 为什么必须订阅 Flow（第一版无法解锁的根因）

`NearbyControlSend.sendControlCmd` 的签名以 `Continuation` 结尾，是 Kotlin
suspend 函数，实现体是 `channelFlow { handleControlCommand(...) }`：

```java
public final Object sendControlCmd(String dkId, BleControlType type,
        CmdChannel channel, int seq, byte[] payload, Continuation cont)
```

用反射传入一个假 `Continuation` 直接调用，**只会返回 `ChannelFlowBuilder` 冷流对象**；
`channelFlow` 的 lambda 在 `collect` 之前一行都不会执行，命令从未发到车端。
第一版把「拿到对象」误判为「已提交」，所以手动点 UNLOCK 也毫无反应。

修正方式：识别返回值是否为 `kotlinx.coroutines.flow.Flow`，是则反射
`FlowKt.launchIn(flow, scope)`，scope 取官方 APP 自己的
`BleEventHandler.scope`（`Dispatchers.IO`，随数字钥匙服务存活）。
这样内部 `handleControlCommand` 才会通过 `IVehDkConnService` 向已连接的车写帧。

**判据**：`pk_recon.txt` 里必须出现 `FLOW_SUBSCRIBED`，
只有 `SEND ... -> ChannelFlowBuilder` 就说明命令没发出去。

## 关键反射入口

```java
// 发送器（活单例）
com.geely.snc.basevehicle.control.ble.NearbyControlSend.INSTANCE
    .sendControlCmd(String dkId, BleControlType type, CmdChannel channel,
                    int seq, byte[] payload, Continuation cont)

// 命令类型（枚举，各带 dk15Cmd / dk20Cmd）
BleControlType.DOOR_UNLOCK / DOOR_LOCK
BleControlType.APPROACH_UNLOCK_OPEN / CLOSE
BleControlType.WALKWAY_LOCK_OPEN / CLOSE     // 注意官方拼写是 WALKAWAY

// 通道
CmdChannel.DK15 / DK20 / ICCE / TSP
```

`sendControlCmd` 是 Kotlin `suspend` 函数，调用时需传一个 `Continuation`。
`DkBridge` 用动态代理构造，协程上下文优先取 `Dispatchers.IO`，
拿不到则退回 `EmptyCoroutineContext`。

## dkId 的来源

发送 BLE 命令需要 `dkId`。它没有明文存在配置里，因此采用三级策略：

1. **自动学习（最可信）**：hook `NearbyControlSend.checkDkBaseListener(String)`
   和 `sendControlCmd(String, ...)` 的首个参数 —— 官方自己调用时传的就是真值。
2. **MMKV 预载**：`dk_userid`（`1234567890123456789`）作为初始候选。
3. **手动指定**：`SETDKID <value>`。

`DkBridge` 会按 `学到的 > MMKV预载 > 手动` 的顺序逐个尝试，**一旦某次提交成功
就立即停止**，避免重复下发同一条控制命令。

## 待实测确认的两点

这两点必须到车边才能验证，代码已就绪但结论未知：

1. **dkId 是否等于 `dk_userid`**
   若不等，需等官方 APP 连接一次后由学习钩子捕获（日志会出现 `LEARN dkId=`）。

2. **车机是否持续广播 BLE 广告**
   RSSI 测距的前提。若车机只在被连接后才广播，本方案需改用车端主动上报事件
   （`ApproachLockNotifyConPayload` 已存在，说明车端有主动通知能力）。
