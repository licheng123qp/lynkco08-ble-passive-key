# 四闸门判定表

> 这份表的作用：让你拿到抓包报告后，**不看代码也能自己判断项目还有没有戏**。  
> 六个字段里四个是硬闸门，任一硬闸门命中就停，不要在死路上继续投入。

---

## 总览

| 闸门     | 问题                        | 靠什么判定      | 类型     |
| ------ | ------------------------- | ---------- | ------ |
| **G1** | 协议是否依赖 BLE 配对绑定（bonding）？ | 抓包（SMP 报文） | 🔴 硬闸门 |
| **G2** | 应用层密钥是否在 TEE / StrongBox？ | APK 静态逆向   | 🔴 硬闸门 |
| **G3** | 是否有防重放（计数器 / nonce）？      | 抓包（写帧差异）   | 🟡 软闸门 |
| **G4** | 是否有车端证书链 / PKI 双向认证？      | APK 静态逆向   | 🔴 硬闸门 |

**通过条件**：G1 否 + G2 可导出 + G3 可解 + G4 否 → 进入实现。  
**任一硬闸门命中** → 停止，转替代方案。

> ### 补充：UWB 的那条信息意味着什么
>
> 领克 08 的 UWB 靠近解锁只支持 iPhone / 魅族。这条信息不影响上表，  
> 但它锁死了一个方向：**别指望车端自己开锁。**
>
> UWB 在数字钥匙里的核心价值是**安全测距**——能证明设备真的在 1 米内。  
> BLE 的 RSSI 用几十元中继器就能骗过，所以车厂放开了 UWB 被动进入却不放 BLE 被动进入，  
> 这是刻意的安全设计，不是遗漏。
>
> 结论：我们的 APP 必须**自己发解锁指令**。于是 G2（密钥能否导出）从"重要"升级为  
> **唯一生死线**——凭证拿不到，方案就不存在（因为已排除复用官方 APP）。

## G1：BLE 配对绑定

### 为什么这条最致命

BLE 的配对绑定（bonding）会在**手机侧蓝牙芯片/系统**里存一份长期密钥（LTK/IRK）。  
这份密钥的归属者是**手机系统的蓝牙栈**，不是某个 APP。

后果：即使你把官方 APP 的协议算法完整抄出来，新 APP 也**用不了那份 bond**。  
而重新配对需要**车端接受**——车规系统通常要求"车内确认 / 物理钥匙在位 / 车机屏幕点确认"，  
你没法在车外自动完成。**所以 G1 命中 = 无感解锁做不成。**

### 怎么判

看报告里的「SMP 配对流程」章节：

| 报告里的现象                                                              | 结论                      |
| ------------------------------------------------------------------- | ----------------------- |
| 显示"无 SMP 报文"                                                        | ✅ G1 通过，协议不走 BLE 层绑定    |
| 有 `0x01 Pairing Request` / `0x02 Pairing Response`，且 `bonding=True` | ❌ G1 命中 → **停止**        |
| 有 SMP 但 `bonding=False`                                             | ⚠️ 需人工确认是否仅加密链路而不存 bond |
| 有 `0x06 Encryption Information` / `0x07 Master Identification`      | ❌ 已分发密钥，等同命中            |

### 容易误判的地方

**"没有 SMP"不等于"没有加密"**。还有两种可能：

1. **应用层加密**：BLE 链路明文，但 ATT 载荷本身是密文。这时候 G1 通过，但看 G2。
2. **Just Works 配对**：SMP 只有两三帧就结束了，容易被忽略。务必看 `0x01~0x04` 有没有出现过。

判断方法：如果写帧载荷看起来是完全随机的字节（不像明文 JSON/ASCII/结构化数据），  
那就是应用层加密，去查 G2。

## G2：密钥存储位置

### 为什么这条决定生死

Android 的 **Keystore** 可以利用 TEE / StrongBox 生成并保管私钥，  
**私钥在物理上无法导出**——你连 root 都读不出来，因为运算发生在独立安全芯片里。

如果钥匙私钥在那儿，那么"把钥匙搬到自己的 APP 里"在技术上就不存在实现路径。  
这不是难度问题，是设计目的本身。

### 三种情形与结论

| 观察到                                                                        | 结论               | 后续                 |
| -------------------------------------------------------------------------- | ---------------- | ------------------ |
| `KeyStore.getEntry()` 取私钥 + `KeyGenParameterSpec` + `setIsStrongBoxBacked` | ❌ G2 命中 → **停止** | 无解，转替代方案           |
| Keystore 里存的是"用设备密钥加密的**密文**"，而设备密钥在 native 里                              | ⚠️ 可行但极难         | 需要脱 native 白盒，工作量大 |
| 密钥来自云端下发，存 SharedPreferences / SQLite，或 native 里硬编码数组                      | ✅ G2 通过          | 最容易，直接提取           |

### 怎么查（阶段 B 用的搜索锚点）

在反编译出的 Java 代码里搜：

```
KeyStore.getInstance("AndroidKeyStore")
KeyGenParameterSpec
setUserAuthenticationRequired
setIsStrongBoxBacked
getKey("...", null)
```

在 native 库里搜字符串：

```
AndroidKeyStore
strongbox
keymaster
```

## G3：防重放机制

### 影响什么

决定难度，不决定可行性。

| 现象                 | 判定              | 实现难度              |
| ------------------ | --------------- | ----------------- |
| 三轮解锁载荷**完全相同**     | 无防重放            | ⭐ 只要重放即可，一两天能跑通   |
| 有固定位置的字节**递增/变化**  | 计数器 / nonce     | ⭐⭐⭐ 要还原算法，需找到计数规则 |
| 长度都不一致             | 变长编码（常含计数器或时间戳） | ⭐⭐⭐⭐ 最难，要完整还原编码器  |
| 变化字节**无规律**（每次全随机） | 随机 nonce + MAC  | ⭐⭐⭐⭐ 必须实现完整加密     |

### 关键：不要只看"字节变了"

要看**变的是哪个字节、怎么变的**。报告里会列出 `varying_offsets`：

- 只有 1~2 个字节在变，且是 `01→02→03` 递增 → **简单计数器**，最容易还原
- offset 在末尾且值随机 → 很可能是 **MAC/校验和**（说明前面有加密）
- 前半段随机、后半段也随机 → **整体加密**

### 计数器的一个隐藏好处

如果是简单计数器，说明车端只校验"必须比上次大"。这种设计一旦还原，  
实现起来非常直接。但要注意：**计数器状态存在手机侧还是车侧**，  
以及**掉电/换手机后会不会失步**——这是实际部署最容易翻车的地方。

## G4：车端证书链 / PKI

### 为什么致命

如果握手是"手机出示证书 → 车端验签到根 CA"，那么：

- 你的新 APP 没有车厂 CA 签发的证书
- 自己签的证书车端不认
- 伪造证书需要车厂根私钥

**没有绕过的可能，只有放弃。**

### 怎么判

在 APK 里搜：

```
X509
CertificateFactory
verify(
TrustManager
ECPublicKey / RSAPublicKey
BouncyCastle / BCECPublicKey
```

如果发现 X.509 证书解析 + 签名验证，且证书不是本地硬编码而是配对时下发 → 基本可判定 G4 命中。

---

## 快速决策树

```
抓包报告到手
    │
    ├─ SMP 里有 Pairing Request + Bonding=True ？
    │      └─ 是 → ❌ G1 命中 → 停，走替代方案
    │
    ├─ 写帧是明文还是密文？
    │      ├─ 明文 → 看 G3（差异分析）→ 若静态帧，可直接试重放验证
    │      └─ 密文 → 进阶段 B 查 G2
    │
    └─ 阶段 B（APK 逆向）
           ├─ 私钥在 AndroidKeyStore/TEE？ → ❌ G2 命中 → 停
           ├─ 有 X.509 证书链验证？        → ❌ G4 命中 → 停
           └─ 都不命中 → ✅ 进入实现
```

---

## 如果停了，还剩什么

按性价比排序：

| 方案           | 成本  | 说明                                       |
| ------------ | --- | ---------------------------------------- |
| **查车机设置**    | 0   | 领克 08 中控里若有「靠近解锁 / 迎宾」开关，打开就好。**这条永远先查** |
| **远离提醒**     | 半天  | 不改协议，只做"人走了但车没锁"的推送提醒，安全性高、合规            |
| **等官方 OTA**  | 0   | 官方后续版本可能补上                               |
| **第三方无感模块**  | 几百元 | 接 OBD/车门模块的独立硬件方案，与协议逆向无关                |
| **复用官方 SDK** | 中   | 技术上最稳，但你已经明确排除了                          |

---

## 一句话总结

> **G1 和 G2 是"能不能做"，G3 是"难不难做"。**  
> 先花一天确认 G1，再花一天确认 G2，两天内就能知道这个项目值不值得投入。  
> 不要反过来先写 APP。
